Things that surprise people

  1. There is no log on a till. log.Printf output goes nowhere in the Windows build. Add a log file before debugging a till by its logs.
  2. Checkout doesn't take stock off. Stock is kashi's, from synced sales.
  3. A product has no price of its own. Prices come only from kashi's price lists; products.price is frozen. Not in an active list = can't be sold.
  4. All money is integer USD cents, whatever was paid with. Expenses and loans are the exception (their own currency, x100).
  5. Attendance isn't polled in the background. Punches come in when the device pings the till, when the till starts, or while the Attendance page is open. Each pull looks back 7 days.
  6. **Raising the attendance duplicate interval deletes punches already imported**, not just future ones.
  7. IN/OUT comes from the device, not from punch order.
  8. The "manager password" is the attendance approver's password, and it also unlocks Expenses, Loans and Conversion.
  9. The PIN lockout survives restarts and doubles each time (30 s up to 30 min).
  10. A missing feature flag means its default, and defaults differ (some on, most off). Read default-on flags with flagEnabledDefaultOn.
  11. Migrations are tracked by number only and must stay additive. An older build runs on a newer database; that's what makes rollback safe.
  12. A bad update rolls itself back: if the new version doesn't confirm it started, the helper restores the old exe.
  13. Kiosk mode closes Explorer. Close App brings it back; a crash needs Task Manager → Run new task → explorer.
  14. Cash machine mode closes every other program every 30 seconds while kiosk mode is on, and its one-time setup removes apps for good.
  15. The scanner is recognised by typing speed (6+ keys under 50 ms apart, ending in Enter/Tab), not by its USB ID.
  16. A stuck Windows key after AnyDesk is released automatically after 3 seconds (till-only switch, on by default).
  17. While connected, the till can't remove products or clients; kashi deactivates them. Nothing anything refers to is ever hard-deleted.
  18. Price lists, payment methods and currencies arrive whole, so something missing from kashi's list disappears from the till.
  19. Sync stops at the first network error and waits for the connection, instead of backing off each row.
  20. Some settings never leave the till: API key, theme, register number, attendance device password, manager password, stuck-keys switch.
  21. Times are read in the branch's time zone, not the PC's.
  22. Stale shifts can be auto-closed at startup (if switched on), and empty ones are deleted rather than closed.
  23. The cashier PIN is stored as plain text; the admin password as unsalted SHA-256.
  24. **The first Windows build after the Go module cache is cleared takes a long time** (SQLite-in-Go is big). Go is pinned to 1.25.5 for Wails.
  25. TestStartupPreservesRuntimeDatabase kills the Go test run (known, since at least v1.1.75).
  26. Animations are off by default, but spinners always spin. The Animations switch only governs the nav rail's red status dot and one menu fade; styles/settings.scss kills every other transition regardless. v1.1.82 switched every till off once.
  27. A layered !important beats an unlayered one. The UI kit's CSS is in @layers, so a page's !important can't override a kit !important.
  28. The empty-cart overlay is blurred on purpose, even on old tills (backdrop-filter, CPU-drawn because GPU rasterisation is off in webview_windows.go). Don't add other blurs or heavy shadows.
  29. **The "Ready to scan" panel and the idle-built calculator are on the ready-state branch**, not on master.
  30. The cart draft is saved ~0.4 s late, on purpose (lib/draftSaver.ts); clearing it is immediate. Never write it straight to localStorage.
  31. Product search has an FTS5 index for terms of 3+ characters and plain LIKE below that; both must return the same rows. It is slower than LIKE for the first page of a very common word.
  32. libphonenumber lives only in the ClientDialog chunk. Importing it from the sale screen's startup path puts ~140 kB back into home.
  33. sqlc is v1.31.1 now, and it generates the FTS queries too. Some EXISTS/COUNT results are bool, not int64.
  34. GB_CLOUD_WEBVIEW_ARGS replaces the WebView2 flags for one till, to compare GPU rasterisation on and off without a rebuild.
  35. cp may be aliased to cp -i in a shell, and hangs a script waiting for "y". Use /bin/cp when copying a database to benchmark on.

These docs were written on 2026-10-31 from the code at v1.1.77; items 26-35 and performance.md were added with v1.1.82. When you change a behaviour described here, update the page in the same commit.

Selling

Money and selling

At a glance

  • Integer USD cents everywhere; rates are units_per_usd_micros. Never compare currency codes to literals.
  • Not in an active price list = no price; checkout refuses a zero price.
  • priceInvoiceTotals is the one pricing path (checkout and live quote), so shown = charged.
  • Returned lines have negative quantity and total; sum as stored.
  • On Account and On Coupon are found by exact name: do not rename.

Code: money.go, currencies.go, pricing_overrides.go, tx_invoice.go, invoice_quote.go, deals.go, invoice_discounts.go, oversell.go, tx_exchange.go, deal_exchange.go, invoice_lbp.go.

How amounts are stored

  • Every amount is an integer in cents of the default currency (USD). Invoice totals, line prices, payments, shift balances: all USD cents, whatever the customer paid with. There is no floating-point money.
  • Exchange rates are currencies.units_per_usd_micros: how many millionths of the currency make one USD, so rates both above and below the dollar fit an integer.
  • Never compare currency codes to a literal. resolveCurrency looks a currency up by code and falls back to the default currency, so a currency added in Settings works everywhere without code changes.
  • products.currency_code is unreliable legacy data (thousands of USD products are tagged LBP). Never convert with it.
  • Expenses and loans are the exception: stored in their own currency, x100, as entered.

LBP

The till shows and prints an LBP total next to USD: the LBP rate, rounded to the LBP cash unit with the branch's rounding mode (invoiceLBPTotal, the same rounding the receipt uses). A refund rounds its size and keeps its sign. auto_append_lbp_zeros (off by default) adds the trailing zeros when typing LBP amounts.

Where a price comes from

  • Since migration 000097 a price is not part of the product. It's an entry in a price list that kashi decides and the sync mirrors down. products.price and products.discount still exist but are frozen: nothing reads them.
  • A product in no active price list has no price, and checkout refuses a zero price. That's deliberate: kashi decides what can be sold. "Can't sell this item" at a till usually means it's missing from the branch's price list.
  • Price and discount lists are read-only on the till.

Pricing a cart

  • priceInvoiceTotals is the one pricing path. Checkout (salesInvoiceTx) and the live preview (InvoiceQuote, the calculator's total) both call it, so the total shown can't differ from the total charged.
  • Deals ("Buy 2 get 1", "2nd 50% off", "3 for $50", "3 or more 20% off"): a discount list row names the deal a variant is on; every unit in the cart on the same deal is pooled whatever its product, and the cheapest units get the reward. A deal replaces a discount: deal units are priced from the list price. The line stores what the deal took off (deal_discount) and the invoice keeps a copy of the deal's terms (invoice_deals), so an exchange is judged by what was sold, not by today's deal.
  • Invoice discounts ("$150 or more, 15% off"): checked on the total after item discounts and deals, before tax, and taken off on top of them. When several apply, the one that saves most wins; they never add up. The discount is spread over the lines in proportion to their cost (invoice_products.invoice_discount), so a return credits what the line was actually paid. Exchanges never earn one.
  • Discount/deal toggles (discount_toggle, deal_toggle): let the salesperson turn a line's discount or deal off. discount_toggle_default_off makes lines start with the discount off. Off by default; kashi can push them.
  • Price edits at the till can be restricted to certain product codes (price_edit_restricted + the code list), and custom prices/discounts are separate switches (custom_item_prices, custom_item_discounts, per_unit_item_prices, price_change_manual_override_mode).
  • kashi's live cart overrides (live_cart.go) beat all of the above for the one sale they were made for: a price, a discount or no deal per line, or every deal off. See sync.md, Live cart.

Stock

  • Checkout doesn't take stock off. The deduction block in salesInvoiceTx is disabled; stock is kashi's job, from the synced sales.
  • invoices.inventory_id is only a label. An unset or unknown sales inventory must never stop a sale; the worst case is a wrongly labelled invoice. Only a database with no inventories at all can't sell. If stock deduction is ever turned back on, this needs revisiting.
  • Selling beyond stock (settings.oversell_mode, set by kashi per branch): allow (sell; kashi flags the negative stock), warn (the cashier confirms first) or block (refuse). "Stock" is kashi's on-hand for the branch minus this till's own sales kashi hadn't received yet. A product kashi reports nothing for counts as 0. If the till has no stock data for the branch at all, nothing is checked: a till must never refuse a sale for lack of data.

Payment methods

  • Payment methods are cashbox accounts, owned by kashi. Retiring one deactivates it; it's never deleted, because invoices and shift balances point at it.
  • On Account (client credit) and On Coupon are internal placeholders that the code finds by exact name. Don't rename them.
  • overchange_confirmation (on by default): ask before giving more change than makes sense. settings.max_overpayment_cents caps overpayment.
  • Revenue is SUM(invoices.grand_total), not the sum of payments, because payment entries include change rounding and unrecorded cash overpayment.

Returns and exchanges

  • An exchange records the returned lines and the replacements; the customer only pays the positive difference.
  • Returned lines are stored with negative quantity and line total; replacements stay positive. Sum them as stored; don't flip signs. Return and exchange invoices have the EX/ and RS/ prefixes.
  • Only quantities not already returned can be returned again.
  • What an exchange returns can change while it's on screen: in exchange mode the toolbar's exchange button opens "Returned items" (ExchangeReturnsDialog.vue, GetExchangeInvoiceByID). It shows the sale's items with a count each, from 0 ("not returned", left on the sale) up to what the sale has left. At least one unit stays returned (cancel the exchange to return nothing). Returned cart lines are built in one place (lib/exchangeReturns.ts), for the dialog and the picker alike.
  • An exchange can be held like a sale (a settlement can't). The hold snapshot carries exchange: {originalInvoiceId, originalInvoiceCode}, and restoring puts the lines back as held: never through addItem, which would turn a returned line into a unit for sale (frontend/src/lib/holdSnapshot.ts). A hold's returned lines without a sale are dropped. Nothing is reserved while it's held, so the quote re-checks the sale when it comes back.
  • A product can sit on several lines of one sale: a deal keeps its paid and free units apart, and the same product scanned at two prices stays apart (invoice_products has had its own id since 000061). Never match a returned item to "the" line of its product; spread the quantity over every matching line (validateAndPriceExchange, executeRemoteReturnInvoiceCommand).
  • Deal exchanges (deal_exchange.go) have their own rules: a paid unit is credited what was paid; a free/reduced unit is credited what was paid plus "swap credit" up to its shelf price, which only buys replacements in the same exchange and is never paid out; and if the customer's remaining items no longer earn the deal saving they still enjoy, the difference is charged back. The amounts ride on the exchange's own lines, so lines still add up to the invoice.
  • The exchange screen shows the quote's amounts, never its own. QuoteExchangeTotal returns one line per cart line sent, in order (exchange_quote_lines.go), and a breakdown. A returned line shows its credit, which is often not its shelf price: what was paid, plus any swap credit, minus any charge back. These always hold, and the quote errors rather than break them:

| Identity | Checked in | | --- | --- | | -credit = paid + swapCredit - chargedBack per returned line | exchangeQuoteLines, exchangeQuoteProblem | | sum(lines) = net = replacements - returned | both | | net + tax = unrounded, max(0, unrounded + rounding) = total | both |

Quote and checkout get the total from one function (computeExchangeTotals). The screen re-checks every quote (frontend/src/lib/exchangeQuote.ts) and shows an error, not a total, when one doesn't add up for the cart it was asked about. Real quotes are written to frontend/src/lib/testdata/exchange_quotes.json by TestExchangeQuoteGolden (rewrite with KASHI_UPDATE_GOLDEN=1) and checked by the frontend tests.

  • An expense or loan entered by mistake is cancelled, not deleted (records_cancel.go): it stays listed as cancelled and stops counting.

Unknown items

Something with no code here (unknown_items.go): the cashier sells it as a placeholder product at a typed price; before payment a phone photographs every unit (QR link from kashi), and the sale is held until each unit has a picture, unless a kashi user with the right permission lets it through. Someone in kashi names the items afterwards. unknown_pictures_at_checkout controls the photo step.

Unknown items join the shop's deal (unknown_item_deal.go): the free-units deal the most products are on in the lists in force, whatever its numbers, pooled with every other unit on it. The salesperson picks one of three on each line by tapping its deal chip: deal else 30%, deal else 20% (the default) or No deal, with the picker naming the real deal; the percent is what a unit outside a set gets, like a discount row's own fallback (kashi 000216). This choice works whatever deal_toggle says. A discount can be typed only with the branch's custom discounts on (its price can always be typed), and it keeps the line off the deal (a deal never stacks on another saving), and picking a deal clears it. With no product on such a deal, unknown items sell at their typed price and show no chip. The cart sends the line's unknownRef as lineRef, and the quote echoes it with the choice in force (unknownDeal), since every unknown item is the same product.

Coupons and client accounts

  • Coupons and coupon types come from kashi.
  • A client's receivable balance is built from the invoices that created it and the payments applied to them (client_accounts.go).
  • RoundInvoice re-applies the current rounding rule to an existing invoice and fixes its payments, account entries and shift balance with it (admins only).

The unfinished sale (draft)

The cart, client, note and calculator state are kept in localStorage (kashi-pos.invoice-draft) so a restart or crash restores the sale. The write is coalesced (lib/draftSaver.ts): about 0.4 s after the last change, or at once when the page is hidden or closed. Emptying the cart (or finishing the sale) deletes the draft immediately and cancels any save still waiting. Settlement mode (paying off an old invoice) never saves a draft.

Shifts and logins

At a glance

  • A sale needs an open shift; expenses and loans do not.
  • PIN lockout survives restarts and doubles: 30 s up to 30 min.
  • The "manager password" is the attendance approver's and also unlocks Expenses, Loans, Conversion.
  • Stale shifts auto-close only if switched on; empty ones are deleted, not closed.

Code: shifts.go, shift_auto_swap.go, shift_upload_server.go, sync_shift_receipts.go, spend_summary.go, app.go (logins), salespersons.go, auth_credentials.go.

Shifts

  • A sale needs an open shift. An expense or loan doesn't (paying a bill before the first shift opens is normal).
  • Stale shifts: with auto_close_stale_shifts on (off by default), a shift opened on an earlier day is closed when the app starts, without counts or a closing person. One with no activity at all is deleted instead, so empty $0 shifts never show up or reach kashi.
  • Opening float (opening_float_enabled, on by default): the cash put in the drawer at the start. Changing the default only affects shifts opened later; ApplyOpeningFloatToCurrentShift changes the open one. Turning the feature off removes the float from every total, receipt and balance.
  • Counting at close (count_opening_cash_on_close, on by default): the cashier counts the whole drawer, float included. Off: they count only what came in during the shift, and the float is left out of both expected and printed figures so the difference still lines up.
  • Negative LBP at close (auto_cover_negative_lbp, off by default): if more LBP went out as change than came in, the shortfall is swapped into USD cash so LBP ends at 0.
  • Close-shift receipt photo (settings.shift_receipt_upload_mode, an enum, default hybrid): a QR code on screen; a phone photographs the printed shift receipt.
    central: the till posts the close to kashi straight away, gets a one-time
    token, and the QR points at kashi.
    local: the QR points at the till's own server (0.0.0.0:8788,
    KASHI_SHIFT_UPLOAD_LISTEN); the photo is forwarded to kashi later.
    hybrid: central, falling back to local if kashi can't be reached.
  • Monthly total on the shifts page (GetMonthSales): counted the way kashi's reports count net sales, so the two agree: every sale by the local day it was rung up (not the shift it fell in), returns netted, cancelled sales and their refunds left out, coupons counted. Under the total it says how much of it is "calculate on checkout" coupons and how much is on account. Each day's figure is that day's sales; a shift row under a day still shows its own whole total. Branch-target progress is different: it still leaves those coupons out.
  • Goodbye (CloseShiftCard.vue): once the shift is closed and the photo is in (or a manager skipped it, or none was needed), the closing salesperson gets a thank-you by name and the choice to shut the computer down (ShutDownComputer, as in the Quit dialog; refused in a development build) or just log out.
  • The shift receipt's sign-off lines (shift_report_signatures, on) and capital-letter header (shift_report_uppercase_header, off) are switches.
  • kashi can correct a closed shift's balances (replace_shift_balance) and reprint its report (print_shift_report).
  • close_shift_requires_sync: see sync.md.

Logins

  • Admin and cashier logins. The cashier uses a shared 4-digit PIN on a keypad. Branch users (and their PINs) come from kashi; kashi can set a PIN remotely (set_branch_user_pin).
  • PIN lockout: 3 wrong PINs lock the keypad for 30 s, and each further lockout doubles it (60 s, 2 min, …) up to 30 minutes. The state is kept in the database (pin_lockout), so restarting the app doesn't reset it: it just leads to a longer wait next time. The legacy kashi-admin can clear it (unlockPINLockout).
  • Credentials are in auth_credentials (since migration 000083). The values the login screen shipped with before that are still the fallback when there's no database or no row.
  • The admin password is hashed with plain unsalted SHA-256; the shared cashier PIN is stored as plain text (auth_credentials.cashier_pin).
  • The manager password is the attendance approver's password (see attendance.md); it unlocks Expenses, Loans and Conversion for a non-admin.
  • Non-admin page access can be locked per page (Settings → Page access; kashi can push it).

Salespersons

  • While connected, kashi owns the roster. A salesperson left over from before the till was connected can still be deleted, but not renamed.
  • salesperson_per_invoice_required (off by default): every sale must name a salesperson.
  • client_required (on by default): every sale needs a client, with an "Anonymous / prefer not to say" option.

Conversion and visitors

  • The nav-drawer people counter (visitor_counter) records walk-ins per day. Turning it off only hides it; the counts stay.
  • The Conversion page divides each day's sales by its visitors, using only days that have a visitor count. Admins pick any range; a manager (manager password) always gets the current month so far.

Targets

Revenue targets come from kashi, read-only. Progress is kashi's branch-wide figure (all registers' synced sales) plus this till's sales kashi hasn't got yet, so a sale moves the bar at once and is never counted twice. Only targets overlapping the current month are shown.

Sync and devices

Sync with kashi

At a glance

  • kashi owns catalogue and prices; the till owns invoices, shifts, expenses, loans, attendance.
  • Match on uid, never integer ids.
  • Every synced write queues an outbox row in the same transaction.
  • A network failure stops the whole pass and waits; a 5xx/408/429 backs off just that row.
  • Never delete what history points at; deactivate. Price lists, payment methods, currencies arrive whole.

kashi is the central server (~/Code/kashi, Go + Postgres). A till works alone when no central URL is set (standalone mode) and syncs with kashi once one is. Code: sync_*.go, commands.go, standalone.go.

Identity rule: sync matches rows on uid (UUID), never on integer ids; the ids on the till and on kashi are separate number spaces. Phone (clients) and barcode (products) are only the fallback for adopting kashi's uid on old rows. Lookup tables without a uid (currencies, cashbox accounts) match on their natural key (code, name).

Never delete what history points at. A product, client, payment method or salesperson that an invoice, coupon, transfer, stock row or account entry refers to is deactivated, not deleted. Only a row nothing refers to is really removed. While connected, only kashi deactivates.

Pushing up: the outbox

  • Every write that kashi must know about queues a sync_outbox row **in the same transaction** as the write. A crash can't leave a sale without its sync row, or the other way round.
  • The push loop drains the outbox: every 15 s, plus a 5 s backstop, plus a "kick" right after a local write.
  • A network failure is about the connection, not the row (pushLink): the pass stops at the first one and the whole loop waits (5 s, 10 s, … up to a minute). The first pass that gets through makes every pending row due at once. A real answer from kashi (5xx, 408, 429) backs off just that row. Rows that failed for good are retried hourly.
  • Rows are stamped with the server they're meant for. The nav-rail sync dot is only green when sync is configured, nothing is pending, nothing failed, and nothing is still stamped for a previous server.
  • close_shift_requires_sync (off by default, kashi can push it): a shift can't close, and its receipt isn't printed, while anything is still in the outbox. The close screen flushes it first.

Pulling down

  • A separate loop, so an outgoing sale never waits behind a catch-up.
  • Entities, in order: currencies, cashbox_accounts, products, price_lists, discount_lists, clients, branch_targets, salespersons, branch_users, expense_categories, loan_categories, coupon_types, coupons, branches, transfer_requests, incoming_transfer_requests, branch_stock, quick_access, invoice_discounts, calendar_events.
  • Each follows kashi's updated_at cursor, which only advances after a whole successful walk. So every apply must be idempotent: a failure mid-page re-applies the same payload next time.
  • Price and discount lists arrive whole (the list with all its items), and the till writes only the rows that differ. Whole is the only way a removed item can disappear, since a delta can't say "this item is gone".
  • calendar_events (the Events page) arrive as the whole set too, and what kashi drops is deleted. The built-in retail calendar is not synced: it is a copy in frontend/src/lib/retailCalendar.ts, to keep in step with kashi's. The same events also show as the "Coming up" card on the Shifts page (components/shifts/EventsCard.vue: next 90 days, 3 at most, in one row).
  • Payment methods and currencies also arrive as the whole set, so a row kashi didn't send is retired (deactivated). Two things kashi can never touch: the On Account and On Coupon placeholder methods (the code finds them by exact name), and the default currency, which every stored amount is in.
  • The completeness check (sync_full_check.go): the cursor only sees changes, so a row the till never got would stay missing forever. This pass compares all client and product uids with kashi's and fetches anything missing or older.
  • Backstop pull every 5 minutes; target progress every minute.

Live link (WebSocket)

kashi pushes nudges over a WebSocket (sync_ws.go): "something changed, pull now", "a command is waiting", "an update is available". It's push only and can sit idle for a long time, so both sides ping; a dead connection is noticed within the pong wait instead of whenever the OS gives up.

Live cart

The sale screen reports its open sale (ReportLiveCart, live_cart.go) on every change and every 20 s, and the till forwards it to kashi's POST /branch/live_cart. It's a view, not a record: nothing goes through the outbox, and a failed report is just replaced by the next. kashi keeps only the latest per register, in memory.

From kashi's app bar (the cart button) someone with pricing rights can send a cart_override for that sale: turn every deal off, or give a line (by barcode) a price, a discount or no deal. These go past the branch's settings: validateAndPriceItems applies them itself whatever custom_item_prices, custom_item_discounts, price_edit_restricted and the toggles say, so the quote and the checkout both charge them. The screen marks those lines "kashi" and locks them.

  • Overrides belong to one sale, named by a ref the screen makes per sale (kept in the draft). A report of another sale drops them; a command for a sale that's gone fails, and kashi shows it.
  • Only a plain sale takes them, never an exchange or settlement.
  • Unknown items can't be singled out (they share one barcode); "every deal off" still takes them off the shop's deal.
  • They live in memory: a till restart drops them and the lines go back to their own prices on the next report.

Settings report

The till sends its settings to kashi (pushSettings), re-sending an unchanged report every hour so kashi's copy heals itself. Never sent: the API key, theme, register number, the attendance device password and the manager password hash. kashi can't change what it can't name.

Flags that default to on must be read with flagEnabledDefaultOn when building the report. Reading them with flagEnabled reports a never-touched till as off while it behaves as on, and kashi then pushes the wrong value back on the next save.

Some settings are deliberately till-only and not in the report at all, for example release_stuck_keys (see windows-till.md).

Two writers for the same value

Where both the till and kashi can change something, the later change wins:

  • Display prefs (quick access rows, text size, theme…): the screen keeps them in localStorage and mirrors them to settings.display_prefs; a push from kashi bumps display_prefs_rev, and the screen adopts the stored prefs whenever the rev is newer than the one it last applied.
  • Quick access mode (till or kashi): each side keeps when its value was chosen and only adopts a newer one. A flip made offline goes through the outbox.

Things that rely on kashi's version

Newer features wait for kashi to announce them in its "hello" (for example quick_access), and an older kashi answering 404 on a route (like /branch/app_update) makes that feature stay quiet instead of erroring.

Re-provisioning a branch

PullBranchHistory imports a branch's own past invoices, expenses, loans and shift closes from kashi into a fresh, empty database (it refuses if any of those tables have rows), seeding kashi's refs so nothing is pushed back. It's best effort: payment-account identity and lines without any barcode or uid can't be reconstructed exactly.

Salesperson ids

kashi used to get only the salesperson's name on a sale, so renaming one split them in two. Sales now carry kashi's salesperson id, and each till reported the ids of all its past sales once in bulk.

Reporting to kashi

After each pull pass the till sends POST /branch/sync/report (sync_report.go), for kashi's Commands page: each entity that failed or applied something, an error that has cleared, and its outbox counts. A pass with nothing new sends nothing, and a long paged pull also sends a running count. It never fails a sync, and an older kashi just answers 404.

It also sends a fingerprint of each list in force, whenever one changes: its row count and a hash of its rows, with the same recipe as kashi's api/list_fingerprint.go, so kashi can check what the till really holds. Change one and you must change the other; a test in each repo pins the same values.

A price or discount list kashi switches off keeps its row here, off and emptied, because sold lines point at it. Deleting one with sales fails and rolls back the whole pull, so nothing else in it arrives.

Attendance

At a glance

  • No background timer: pulls on the device ping, at start, and every 60 s while the page is open.
  • Each pull looks back 7 days; only the first 2000 records are read.
  • Raising the duplicate interval deletes punches already imported.
  • IN/OUT comes from the device, not punch order.

How punches get from the Akuvox door device into the till and on to kashi, and the rules that decide which punches count. Code: attendance.go, attendance_push_server.go, attendance_probe.go, attendance_recorded.go.

Where a punch comes from

The till asks the device; the device never sends punches by itself.

When the till pullsWhat triggers it
Right after a punchThe device calls http://<till>:8789/attendance/ping ("Action URL" → "Relay Triggered" on the Akuvox). The till waits 0.5 s (the log entry may not exist yet), pulls, and retries once 1.5 s later if nothing new came in.
When the till startsOne pull, to catch punches made while it was off (the last person out after closing).
Every 60 s while the Attendance page is openThe page's own refresh.
Nothing elseThere is no background timer. If the ping isn't set up on the device and nobody opens the Attendance page, punches wait for the next restart.
  • The ping carries no data and no trust. It only wakes a pull of the device the till already polls, and it's refused (403) unless it comes from the configured device IP.
  • The ping listener address is 0.0.0.0:8789, overridable with KASHI_ATTENDANCE_PUSH_LISTEN.
  • The red/green attendance dot on the nav rail is a separate, cheap TCP connect to the device every second (attendance_probe.go). It says nothing about whether punches are being imported.
  • Pulls are serialized (attendanceSyncMu), so the ping, startup and the page never import at the same time.

What a pull asks for

POST http://<device>/api/doorlog/get, basic auth with the configured user, 15 s timeout, asking for Status: Success punches from 7 days before the date to the end of that date (attendanceLookbackDays).

  • Until v1.1.75 (2026-10-30) it asked for that day only, so a punch made while the till was off was never fetched again. Anything older than 7 days that was missed then is still missing; nothing back-fills it.
  • The code assumes the device may ignore the dates and send its whole history newest first. Only the first 2000 records of the answer are looked at.
  • Only Success punches are used. Failed or denied attempts are ignored.

Which punches are imported

For each punch, in order:

  1. Device user linked to a salesperson? The punch's device user ID must equal a salesperson's attendance_user_id. If not, it's not imported (see "Unlinked punches" below).
  2. Deleted or replaced by an approved request before? The device keeps every punch forever and sends it again on every pull. A punch whose device event ID and time are in attendance_event_audit was taken away by an approved change and is skipped. Matched by event ID and time, not device IP, because the IP can change.
  3. Duplicate? Two punches by the same salesperson on the same day closer together than the duplicate interval (Settings, seconds; 0 = off) are one punch. Only the first is kept.
  4. Otherwise it's inserted into salesperson_attendance_events (`INSERT OR IGNORE`, so re-pulling is harmless) and queued for kashi.

Surprises:

  • The duplicate interval also deletes existing rows. Every pull first runs collapseAttendanceDuplicates over the whole table, so raising the interval removes punches that were already imported, not just future ones.
  • Every pull also deletes any live device punch that matches an audit copy (cleanup for an older build that re-imported removed punches).
  • IN/OUT comes from the device's Type field, not from the order of the punches. The till never works out "first punch = in".
  • Times are read as the branch's local time (see docs/dev/data-and-config.md, "Time zones").

Unlinked punches

A punch by a device user linked to no salesperson (a visitor, or an employee enrolled twice or under a new number) is not attendance, but since v1.1.75 kashi is told about it: it's sent once with status Skipped: unlinked, and attendance_skipped_sent (migration 000134) remembers which were sent, since the device returns them on every pull. kashi keeps them out of worked hours and lists them so someone can link the user. Linking the user later doesn't turn the old skipped punches into attendance by itself.

Only sent when sync is configured.

Fixing punches: requests and approval

A cashier can't edit a punch. They file a request (SubmitAttendanceComplaint):

ActionMeaning
addA punch the device never recorded (forgot to clock, reader missed).
replaceChange an existing punch's time and/or IN/OUT.
deleteRemove an existing punch.
  • The request is stored as pending and sent to kashi (acr-<id>-complaint).
  • It's decided either on the till with the manager password (ApproveAttendanceComplaint), or in kashi, which sends a review_attendance_request command. Both run the same code (reviewAttendanceComplaint).
  • Only a pending request can be decided; a second decision is refused.
  • Approving replace/delete copies the original punch to attendance_event_audit and deletes it; replace/add insert a new punch with device_id = 'manual', event_id = change-request-<id>, status Approved. The new punch goes to kashi like any punch, labelled with who approved it.
  • AddAttendanceWithManagerApproval files an add and approves it in one step, so it leaves the same trail.
  • Manager approval on the till can be turned off per branch (attendance_manager_approval, on by default, kashi can push it). When off, requests wait for kashi.
  • CreateManualAttendanceEvent (the legacy kashi-admin tool) records a punch with device_id = 'admin-manual' and no request.

So device_id tells you where a punch came from: the device IP, manual (approved request) or admin-manual.

The manager password

There is one manager password per till, stored as attendance_config.approver_password_hash. Despite where it lives, it's the manager password for everything: attendance approvals, opening the Expenses and Loans pages, the Conversion page. An admin login skips it. It never leaves the till (kashi has no column for it).

Hashing is plain unsalted SHA-256 (hashPassword in app.go), the same as other till passwords.

Other settings

  • attendance_cashier_history: lets cashiers see attendance history.
  • The device IP, user, password and enabled flag live in attendance_config. The password never leaves the till; the rest is in the settings report to kashi.
  • The "checked in" popup only shows for punches less than 2 minutes old, at most 5 at a time, so a catch-up import doesn't flood the screen.

Sync and devices

The Windows till

What the app does to the Windows PC it runs on. All of it is Windows-only (*_windows.go); on other platforms these are no-ops. Most of it is off in wails dev builds.

Kiosk mode (kiosk_windows.go)

While the app runs, the till shows nothing else:

  • Explorer is asked to exit (the same clean exit as the old "Exit Explorer" menu item, so Windows doesn't restart it). No taskbar, Start, tray, desktop or notifications.
  • The till's window stays on top, and when another program takes focus the till takes it straight back, so a scan never types into another window.
  • A system-wide keyboard hook makes the Windows key, Alt+Tab, Alt+Esc, Ctrl+Esc and Alt+F4 do nothing while the till is in front.
  • Minimized windows aren't drawn.
  • Other programs are closed (cash machine mode, below).

Programs allowed in front of the till (kioskAllowedPrograms): Task Manager, the Windows admin prompt, Tailscale (tailscale-ipn.exe) and AnyDesk.

Getting out: Quit → Close App starts Explorer again. Shut Down and Restart leave it off (the PC is going down anyway). If the app crashed: Ctrl+Shift+Esc → Task Manager → Run new task → explorer. Nothing is stored, so a reboot always brings Explorer back.

Turn kiosk mode off on a till with KASHI_KIOSK=false (in a .env next to the exe).

Cash machine mode (cash_machine.go)

Tills came with dozens of startup programs eating CPU and memory.

  • Every launch, while kiosk mode is on: the user's own startup entries are switched off (the same switch as Task Manager's Startup tab, so they can be turned back on there), and every other program the user runs is closed, again every 30 seconds. Windows' own programs and services are never touched.
  • Once, from Settings → General → "Make this a cash machine" (needs a Windows admin's approval): machine-wide startup entries and third-party scheduled tasks off, apps a till never uses removed, background services off, no sleep, Windows Update outside opening hours. **Removed apps don't come back by themselves.**
  • Kept: GB Cloud and its WebView2 and update helper, AnyDesk, touch screen drivers, the on-screen keyboard, Task Manager.

Starting with Windows (autostart_windows.go)

The app writes its own entry under HKCU\...\CurrentVersion\Run on every launch (not the installer), so tills that only ever got updates from kashi have it too, and a moved install fixes itself. Turning it off in Task Manager's Startup tab still works: that choice is kept in a separate StartupApproved key the app never touches.

WebView2 profile (webview_windows.go)

The webview's profile lives in %LOCALAPPDATA%, not the default %APPDATA%\GB-Cloud.exe. The default folder caused "Microsoft Edge can't read and write to its data directory" when an elevated run (the installer's "Run GB Cloud" checkbox) created it first. The folder is test-written before use; if that fails a temp folder is used, since losing the webview cache is harmless.

WebView2 flags (webview_windows.go, webview_args.go)

WebView2 starts with --disable-smooth-scrolling --disable-gpu-rasterization --disable-gpu-vsync. Nobody recorded why, and turning GPU rasterisation off makes every effect (shadows, opacity) CPU-drawn, which can be slower on a machine whose GPU works. To compare on one till without a rebuild, set the user environment variable GB_CLOUD_WEBVIEW_ARGS and restart the app:

  • unset: the defaults above (nothing changes);
  • a value: used instead, e.g. --disable-smooth-scrolling to try GPU rasterisation on;
  • empty: no extra flags at all.

A WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS already in the environment wins over both. Compare scrolling the invoice list, typing in product search and the checkout screen, then decide on a default. The flags in use are logged at startup (and, like all logs on a till, go nowhere unless a log file is added).

Splash (splash_windows.go)

A plain native window with the logo appears within milliseconds of launch and covers the seconds before WebView2 can paint. It closes on OnDomReady, or by a safety timer if that never fires. It logs to %TEMP%\kashicloud-splash.log.

Devices on the nav rail (devices.go, devices_windows.go)

  • Scanner vs keyboard: both reach Windows as keyboards. A hidden window reads raw keyboard input, which names the device each key came from, and the till learns which device is the scanner from how it types: 6 or more keys, each under 50 ms apart, ending in Enter or Tab. Nobody types that fast. It's remembered in devices.json (next to branches.json); a new scanner replaces the old one on its first scan.
  • Keys injected by AnyDesk or the on-screen keyboard have no device and are ignored for this.
  • Keyboard: any other USB keyboard plugged in. Mouse: any USB mouse that isn't a touch screen (Windows lists touch screens as mice).
  • Printer: Windows' spooler status for the receipt printer in Settings; a USB printer shows offline when unplugged or off.
  • Finding the printer again (Devices dialog, admins): a USB receipt printer plugged into another socket often comes back on a new port (USB002) or as a new printer ("POS-80 (Copy 1)"). The dialog lists printers, their ports, and which USB ports have a printer on them right now, so the admin can switch.

Stuck keys (stuck_keys.go)

AnyDesk from a Mac sends ⌘ as the Windows key. When the Mac keeps a key's release to itself (⌘+Tab away from AnyDesk), the till never hears it come up: Windows keeps holding Win, so typing 1 does Win+1 and every scan fires shortcuts, until someone presses Win on the till. AnyDesk's "Transmit keyboard shortcuts" off doesn't prevent it.

The device listener tracks which modifiers a real keyboard or scanner on the till is holding. Every second it checks which modifiers Windows thinks are held; any (Win, Ctrl, Alt, Shift) held by nothing on the till for 3 seconds is released with an injected key-up. The kiosk keyboard hook lets that key-up through (it's marked with stuckKeyRelease in dwExtraInfo).

Switch: Settings → General → Stuck keys (release_stuck_keys, on by default). Till-only on purpose: kashi doesn't see or push it. It exists for our own remote sessions and isn't something to offer customers (noted in kashi's roadmap, M9).

Time zones (clock.go)

Times are stored in UTC, and days and hours are read in the branch's time zone (kashi's branches.timezone), not the PC's. The app sets Go's time.Local to it, which also covers SQLite's localtime. Migrations (migrations.go, db/migrations)

  • Migrations are embedded and tracked by version number only, not by content. Editing a migration that already ran somewhere does nothing there. That drift has happened; the ensure*Column functions repair databases that recorded a version as applied but miss its columns.
  • A newer schema counts as current: an older build runs on a database a newer build migrated. That's what makes rollback safe, so **migrations must stay additive** (add tables and columns; don't drop, rename or change meaning).
  • Very old databases didn't record versions; they're treated as migrations 1–16.
  • Queries are generated with sqlc (db/query → db/sqlc), v1.31.1. See releases-and-builds.md for the regeneration gotchas.

Product search index (products_search.go, migration 135)

The sale screen's product search (ListProductsCursor, CountProductsForSearch) no longer scans every product with LIKE '%x%'. products_search is an FTS5 trigram table (rowid = products.id; all_text = name + code + barcode, code_text = code + barcode for the code-only switch), kept current by triggers on products, so every writer (sync, CSV import, edits, an older build) stays correct without Go changes.

  • Terms of 3+ characters use the index; 1-2 characters fall back to the old LIKE queries (a trigram index can't answer them). Same rows either way.
  • The queries are generated by sqlc (ListProducts*Indexed, CountProducts*Indexed in db/query/product.sql). ListProductsPage (the products page, the admin server) still uses LIKE.
  • On a 13.9k-product database it takes selective searches (codes, barcodes, rare words) from ~5 ms to ~0.2 ms. A very common word (2,400 matches) is no faster: the first page is slower (~6 ms vs 1 ms) and the count a bit faster.
  • Adding the migration to a big catalogue backfills the index (0.8 s for 13.9k products, once).

How it is put together

  • Components are K*.vue files in frontend/src/ui, registered globally by src/ui/index.ts and used as <k-btn>, <k-card>, <k-text-field>... The names and props follow what Vuetify had, but **only the props, variants and slots the app actually uses exist**. Adding a prop is fine; adding a component the app doesn't use is not.
  • Types: src/ui/global.d.ts declares the components, so templates are type-checked by vue-tsc.
  • No transitions, no ripples. Only the spinners move (k-progress-circular, k-progress-linear, the print spinner, the startup loader's), and they **always spin, whatever the Animations switch says**: they mean "working". Their rules carry !important to get past the global kill in styles/settings.scss.
  • Animations are off by default, on every build (lib/animationsDefault.ts). Before v1.1.82 they defaulted on, so the first start of that version switches every till off once (marker kashi-animations-reset-v1); a switch-on in Settings or a push from kashi afterwards is kept. The animations-disabled class sits on <html> (dialogs are teleported out of the app root). The switch now only governs the red status dot in the nav rail (solid red when off, pulsing when on) and the invoice salesperson menu's fade.
  • Closed overlays cost nothing. Dialogs, menus, tooltips and snackbars are rendered only while open, and teleported to <body>. Without a v-model (<k-menu> / <k-dialog> with an #activator) they keep their own open state.

CSS

  • src/ui/ui.css (components) and src/ui/utilities.css (the d-flex, pa-4, text-center... classes the app uses) live in cascade layers (k-core, k-components, k-utilities). Any unlayered CSS, such as a page's <style scoped>, therefore always beats them, the same as it did with Vuetify. Don't remove the layers.
  • Theme colours are CSS custom properties set on <html> by src/ui/theme.ts as r,g,b triplets: rgb(var(--k-theme-primary)), rgba(var(--k-theme-on-surface), .12). Also --k-border-color, --k-border-opacity, --k-medium-emphasis-opacity... The theme class is k-theme--light / k-theme--dark on <html>.

Performance

At a glance

  • Old tills are the target: read the rules before adding UI.
  • Animations are off by default but spinners always spin.
  • The empty-cart blur is deliberate; do not add other blurs or heavy shadows.
  • The cart draft saves ~0.4 s late on purpose (draftSaver.ts).
  • FTS5 search for 3+ characters, LIKE below; both must return the same rows.

The till runs on old Windows PCs: slow CPUs, little memory, spinning disks, and often a GPU the WebView can't use well. Most "it feels slow" reports come from there, not from a developer machine. This page records what we did about it, why, and the traps that are easy to walk back into. The v1.1.80 move off Vuetify (see ui-components.md) was the big one; v1.1.82 added the rest.

Numbers on this page come from a Mac, not a till. Treat them as ratios, not as what a cashier will see. Anything marked unmeasured is reasoning, not data.

The rules (read this before adding UI)

  1. No infinite animations, no transitions. They force repaints on a WebView that draws on the CPU. Spinners are the only exception (see Animations).
  2. **Think twice before backdrop-filter, filter: blur() or big or layered box-shadow.** With --disable-gpu-rasterization (see WebView2 flags) each is computed on the CPU, on every repaint of whatever sits behind. The one blur we keep on purpose is the empty-cart overlay (see "The blur" below); don't add another without measuring.
  3. Never write localStorage or JSON.stringify the cart on every key. Use lib/draftSaver.ts.
  4. No deep watchers on the cart unless they do almost nothing. The cart changes on every scan and every key.
  5. No unindexed LIKE '%x%' over a big table (products, clients, invoices) on a keystroke. Products have a trigram index for this; nothing else does.
  6. Heavy libraries go in their own chunk, loaded when needed (defineAsyncComponent / import()), not imported statically from the sale screen. libphonenumber is the example.
  7. Lists page. Cursor or offset paging from Go, 20-100 rows at a time. Never load a whole table into the screen.
  8. Don't add a polling loop without checking the table under Background work.
  9. Don't add a dependency for something small. The bundle is parsed on every start; see the sizes below.
  10. Measure on throttled hardware (Measuring, below) before and after.

Rendering

WebView2 flags (webview_windows.go, webview_args.go)

WebView2 starts with --disable-smooth-scrolling --disable-gpu-rasterization --disable-gpu-vsync. No commit message says why. The consequence: everything is rasterised on the CPU, so shadows, opacity changes, blurs and large repaints cost real time. Disabling GPU rasterisation is sometimes slower on a machine whose GPU works; nobody has measured it on a real till.

GB_CLOUD_WEBVIEW_ARGS (user environment variable) replaces the flags for one till, so the two can be compared without a rebuild. See windows-till.md. The default has deliberately not been changed: that decision waits for measurements on an old PC.

Animations

  • Off by default on every build (lib/animationsDefault.ts). Before v1.1.82 the standard build defaulted to on, so the first start of v1.1.82 switches every till off once (marker kashi-animations-reset-v1 in localStorage). After that a switch-on in Settings, or a push from kashi, is kept.
  • styles/settings.scss already kills every transition and animation with !important, whatever the switch says. So "animations on" only brings back the few things that escape that rule on purpose.
  • Spinners always spin, switch or no switch (k-progress-circular, k-progress-linear, .print-spinner, the startup loader's). They mean "working". They escape the global kill with their own !important.
  • The switch now governs only the red status dot in the nav rail (solid red off, pulsing on) and the invoice salesperson menu's fade. It is scoped with :root:not(.animations-disabled).
  • The animations-disabled class is on <html>, not just on the app root, because dialogs and menus are teleported to <body>, outside the root.
  • Cascade-layer trap: ui/ui.css lives in @layers. For !important declarations the layer order reverses, so a layered !important beats an unlayered !important. That is why the spinner rules inside ui.css beat the global kill in settings.scss, and why an unlayered override can't turn them off again. Remove the !important or edit the layered rule itself.
  • kashi's branch settings form defaults animations to off now too (~/Code/kashi, branch-settings.vue). The tri-state "Leave as is" in the default-branch settings is unchanged.

The blur

The empty-cart overlay on the sale screen (home.vue) has backdrop-filter: blur(4px) over a 10% dark layer. It is kept on purpose, on every till including old ones: it was removed once for speed and put back because the look matters more. Know the cost: it is drawn on the CPU and repainted whenever the calculator behind it changes (a keystroke, a total). If an old till feels slow on the empty sale screen, this is the first thing to suspect (unmeasured). Don't add new blurs.

Startup

The sequence, in order, and who pays for each step:

  1. Native splash (splash_windows.go): a plain Win32 window with the logo, up within milliseconds. Covers the seconds before WebView2 can paint. Closes on OnDomReady or a safety timer.
  2. index.html's #startup-loader: static HTML and CSS, no JavaScript framework, covering the app until WaitUntilReady returns. It places the logo where the login page draws it (startupLogoSpot in localStorage) so there is no jump. Its spinner always spins. index.html is ~34 kB because the logo is embedded twice as base64; a small parse cost.
  3. Go: WaitUntilReady: opens the database, runs migrations, starts the workers. This is the real wait. It happens whether or not a loader is up; the loader only hides it. If startup is slow on a till, look here first (unmeasured: add timestamps around it before guessing).
  4. Vue mounts, router-view renders once startup is done, and the page chunks are prefetched in the background.

The loader is not what makes startup slow. Removing it would only show a blank or half-built screen for the same time.

Things loaded at startup, and how to keep them cheap

  • Fonts: Roboto latin and latin-ext only, weights 400/500/700 (main.ts). The full packages also declare Cyrillic, Greek, Vietnamese and symbol faces the till never shows. The Twemoji flag font is fetched up front with document.fonts.load so the client dialog's first open doesn't wait for it.
  • Icons: lib/icons.ts registers only the MDI icons the app uses, instead of shipping the whole set. The price is that **an unregistered mdi-* name renders as text**; scripts/check-icons.mjs (part of pnpm build) fails the build on one. See AGENTS.md.
  • libphonenumber is the single biggest dependency. It is imported only by ClientDialog.vue, which ClientButton.vue and AccountDialog.vue load with defineAsyncComponent:
    ClientButton prefetches the chunk when the browser is idle after mount
    (requestIdleCallback, 5 s timeout; 2 s setTimeout where it doesn't exist).
    The dialog component is created on first open (v-if on a "loaded" flag) and
    then kept, so its close/reset behaviour is the same as before.
    Don't import libphonenumber-js from anything on the startup path. We use
    libphonenumber-js/mobile (not /min) because mobile-type validation is needed, and lib/phone.ts has Lebanon-specific rules around it.
  • Sounds (lib/sound.ts): imported as asset URLs; a new Audio(url) is made for every play. Cheap enough, but it is not a preloaded pool (unmeasured).

The sale screen

Pricing a sale

  • Quotes are not debounced: refreshQuote runs on a 0 ms timer, only to fold changes made in the same tick into one request. quoteRequestToken drops a reply a newer request superseded. This is deliberate; see the comment in home.vue.
  • A quote is cheap because Go keeps the active prices and discounts in memory (pricing_overrides.go). It re-reads them only when the pricing_version row has moved. Triggers on every table that affects pricing bump that row (migration 127), so a sync or an admin edit can never leave a stale price. A new table that affects a price needs the same triggers.
  • The quote watcher is deep on the cart ({ deep: true, immediate: true }). It is the one place a deep watch is justified; keep its work to "start a request".

The draft (lib/draftSaver.ts)

The cart, client, note and calculator state are kept in localStorage["kashi-pos.invoice-draft"] so a crash or restart restores the sale.

  • Saved ~0.4 s after the last change, built from the state at that moment, not when it was queued. Burst edits cost one write.
  • Removing is immediate and cancels a pending save. If it didn't, a save queued just before checkout could write the finished sale back, and the till would offer to restore it after the next restart.
  • Flushed on visibilitychange (hidden), pagehide and when home.vue unmounts, so closing the app doesn't lose the last edit.
  • Settlement mode and the restore itself never save (buildDraft returns null; the watcher also cancels any pending save when entering them).
  • If you add state to the draft, add it to buildDraft() and the InvoiceDraft type.

Focus and observers

home.vue runs a MutationObserver on document.body (subtree, class and style attributes) to re-focus the barcode field after dialogs close. It fires on any class or style change anywhere in the document, debounced by 50 ms. It is a known hotspot and unmeasured. Don't add more body-wide observers; if it shows up in a profile, narrow it to overlay containers.

Product search index (migration 135)

products_search is an FTS5 table with the trigram tokenizer. rowid is products.id; all_text is name || ' ' || code || ' ' || barcode and code_text is code || ' ' || barcode (for the code-only switch). Three triggers on products (insert, update of id/name/code/barcode, delete) keep it current, so every writer stays correct without Go code: the sync pull, CSV import, edits and an older build running on the same database.

  • Terms of 3+ characters use the index (ListProducts*Indexed, CountProducts*Indexed, generated by sqlc); 1-2 characters use the old LIKE queries, because a trigram index can't answer them. searchUsesIndex (products_search.go) is the switch. Both must return the same rows; the tests in products_search_test.go compare them directly. If you change either side, the other must change with it.
  • Matching is case-insensitive, like LIKE. The trigram tokenizer folds Unicode case a bit more broadly than LIKE's ASCII-only rule; no practical difference for our data.
  • % and _ in a term are not escaped, same as before.
  • Migration 135 backfills the index: ~0.8 s for 13.9k products, once.
  • ListProductsPage (used by the admin server; no till page calls it now) still uses LIKE.

Timings, 13,851 products, Mac, list = first page of 21, count = total matches:

Releasing

  1. Finish the work and commit it. make bump refuses if anything is uncommitted, if nothing was committed since the last release, or if the code doesn't build. It writes the version into wails.json and the installer (Windows wants 4 parts: 1.1.77 → 1.1.77.0), commits only those two files, and tags v1.1.77.
  2. make publish builds whatever is on disk at the latest tag's version, so publish right after bumping, from a clean tree.
  3. Choose which tills get it on kashi's App Updates page (or use publish-all).

publish needs KASHI_URL and KASHI_USER; the password is asked once and kept in the macOS Keychain. The release-signing key is in ~/.config/gb-cloud/ (back it up); its public half is compiled in from internal/updatekey. Builds without it never install updates.

How a till updates (updater.go)

  • kashi tells each till which release to run. The till downloads it in the background (resuming partial downloads), checks size, SHA-256 and the release-key signature, and waits for a safe moment: the cashier taps "Install now", or it offers itself with a cancellable countdown once no shift is open (after close shift, or overnight). A forced update is offered right away with a countdown that can't be cancelled.
  • Installing hands off to a helper (a temporary copy of the old exe run with --apply-update): it waits for the app to exit, swaps the exe, starts the new one and waits for it to call ConfirmAppStarted. **If the new version doesn't confirm, the helper puts the old exe back and starts it.** A bad build can't leave a shop without a till.
  • The previous exe is kept next to the current one. "Roll back" in Settings swaps them (and again to go forward).
  • The database is never touched by an update. Rollback only works because an older build accepts a newer schema, so migrations must stay additive (see data-and-config.md).
  • A till only gets updates of its own flavor (standard or compact).
  • A kashi without the update route (404) just means no updates; the till stays quiet.

  • Patches need the old builds: every published build is kept in ~/.config/gb-cloud/releases/<flavor>/<version>.exe; a missing one is downloaded from kashi if kashi still has its file. No old build, no patch: those tills just get the 9 MB download.
  • The till sends kashi its own exe's SHA-256 (have=), so a patch is only offered for exactly the exe it was made from.
  • The signature and checksum are always the plain exe's: whatever arrives is unpacked and checked like before. A patch or zstd file that doesn't rebuild the signed exe is thrown away and the next, bigger download is tried.
  • Adds ~0.2 MB to the till's exe (klauspost/compress).

Build gotchas

  • Go toolchain is pinned to go1.25.5 in the Makefile (GOTOOLCHAIN): Wails' package loader breaks under Go 1.27. Plain go commands outside make may use a newer Go; that's fine for tests but not for wails build.
  • The first Windows build after the Go module cache is cleared is slow. It downloads every module again, and modernc.org/sqlite + modernc.org/libc (SQLite translated to Go) are large to download and to compile. On 2026-10-31 the cache had been wiped and one 18 MB module took ~12 minutes at ~24 KB/s. Later builds use the cache.
  • wails build runs go list -export over the whole project first, to generate the frontend bindings, before the Windows compile. That's a second full compile for the Mac. The bindings (frontend/wailsjs) are committed.
  • After adding a Go method the frontend calls: run wails generate module, then git checkout frontend/wailsjs/runtime (it rewrites the runtime too), and commit frontend/wailsjs/go.
  • sqlc is v1.31.1 (make generate). It turns some EXISTS/COUNT results into bool (ClientHasInvoice, ShiftCloseSyncedForRef, ListInvoices*.IsSale); the callers use them as bools. The FTS5 product search queries (ListProducts*Indexed, CountProducts*Indexed) are generated too: sqlc reads the products_search virtual table from migration 135.
  • Icons: the app doesn't use the MDI webfont. Every mdi-* name must be imported from @mdi/js and added to iconPaths in frontend/src/lib/icons.ts, or it renders as text. pnpm build runs scripts/check-icons.mjs and fails on unregistered names.
  • frontend/src/pages/settings.vue (and some Go files) aren't Prettier/gofmt clean as committed. Run formatters on what you changed only, or the diff fills with unrelated reformatting.
